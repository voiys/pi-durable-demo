## 2. API
Define the agent (AG/docs/agents/harnesses/pi.md:23-59):
```ts
export class Assistant extends Agent<Env> {
  ai = createAI({ binding: this.env.AI }); registry = createRegistry();
  harness = new PiHarness({ harness: ({storage, context}) => { const models = createModels(); models.setProvider(...); return Harness.open(storage, {models, registry: this.registry}, context) }, defaults: { model, thinkingLevel } });
  constructor(ctx, env) { super(ctx, env); this.lifecycle.use(this.harness); }
}
```
The example (AG/examples/next/harnesses/pi/src/server.ts:22-78) uses plain `DurableObject` + `Lifecycle.install(this).use(this.webSockets).use(this.harness)` (server.ts:76-78), `routeAgentRequest` (server.ts:94).
- PiHarnessOptions = { harness: factory({storage, context}) => pi Harness, defaults?: {model, thinkingLevel} } (AG/packages/agents/src/harness/pi/harness.ts:155-161, 98-118, 135-143). Model in defaults is stored as {provider,id} only and resolved at each request against the Models the factory opened (harness.ts:121-129; docs pi.md:68).
- Persistence: pi's own SqliteStorage over `ctx.storage.sql`, all tables prefixed `pi_` (AG/packages/agents/src/harness/pi/session-store.ts:9-39 default prefix at :31). Transcript = immutable entries; documents, tasks, submissions all in that SQLite (PI/packages/durable/README.md:80-103 concepts). Partial answers/tool output committed every <=100ms (README:406).
- Recovery: one Lifecycle wake job per session `pi-wake:<session>` (harness.ts:78-82), heartbeat 30s, wait budget 10min, 60s sleep threshold (harness.ts:49-63); docs pi.md:190-194.
- Session API: prompt/submit/wait/steer/abort/pending/messages/events/reset/setModel/busy; `harness.sessions.create/fork/get/list()` (list includes subagent-created sessions) (pi.md:155-186; harness.ts:680-683 events(), :719 fork, :733 list).
- Streaming: PiHarness provides NO chat protocol (pi.md:9). `session.events()` returns pi's AgentEventStream (snapshot then one batch per commit; harness.ts:680-683). The example puts it on hibernatable WebSockets via `agents/websockets` `WebSockets` capability (AG/examples/next/harnesses/pi/src/sockets.ts:60-102, protocol.ts:17-48) and the browser uses `useAgent` from `agents/react` (use-pi-session.ts:1,34-63) plus a reducer (view.ts). It does NOT use useAgentChat/AIChatAgent. After eviction `reattach()` re-opens watches in onStart (sockets.ts:92-102, server.ts:81-83).
- Without PiHarness, raw pi-durable: `watchEvents(harness, conversationId, ctx)` (earendil-cf post) and `conversation.viewState()/watch()` (PI/packages/durable/README.md:378-406).
- Sub-agents: no PiHarness-specific API. A subagent is an ordinary pi-durable conversation OWNED by the tool task that created it: inside a tool's `api.commit` do `tx.createConversation({ownership:{kind:"task", taskId: api.taskId}})`, `configure(tx, id, {model, extensions:{remove:[Subagent]}})`, `api.details({conversationId})` so the UI can attach, then `(await api.conversation(id)).submit({type:"input", content, requestId:`subagent:${api.taskId}`}).wait()`; tool must be `replay:"safe"`; rerun finds child via `tx.scanConversations({ownerTaskId})` (PI/packages/durable/README.md:534-568; PI/packages/durable/test/examples/22-subagent-foreground.ts, 136 lines). Background/persistent variant with one `subagent` tool (spawn/send/stop/status), background anchor tasks (`background:true`) and reporter tasks that post answers back as followUp: README:574-579, test/examples/23-subagent-background.ts:1-5,59,86-115,133-200. Real-world: Earendil's `search_history` subagent in the walkthrough. Abort/ownership semantics README:570-574. Task graph: README:608-622.
- Custom tools: `ToolRegistration` plain object (name, description, TypeBox `parameters`, `replay:"safe"|"unsafe"`, `execute(args, api, ctx)` -> {output, details, structuredOutput, usage, control}) installed through `registry.install({name, tools, sections})` (AG docs pi.md:70-111; PI README:110-170); `defineTool`/`defineExtension`/`section`/`hook(ToolTask,{beforeTool})`; tools can call tools (`api.executeTool`, README:172-196), `callers` restricts, `deferred` + tool_search for big toolsets (README:198-214), code mode QuickJS (README:220-233). api.memo() survives eviction (pi.md:108). Replay-unsafe tool interrupted by eviction -> model sees `interrupted` result (pi.md:107).
- "optchat": could not identify what is meant (no ctx label, no match in pi-durable source). Left as an open question.

## 3. Model/provider plumbing and SIWC
Flow: PiHarness factory -> `Harness.open(storage,{models: Models, registry, settings},ctx)`. A session stores model as {provider, modelId}; generation resolves `runtime.models.getModel` (PI/packages/durable/src/harness/generation.ts:205) and calls `runtime.models.streamSimple(model, {messages}, options)` (generation.ts:431). Options pi-durable passes: `...settings.stream`, `signal`, `sessionId` (per-conversation UUIDv7), `reasoning` (generation.ts:213-218). It never passes apiKey, maxTokens, temperature, previous_response_id. `settings.stream` type allows transport,timeoutMs,maxRetries,maxRetryDelayMs,headers,metadata,cacheRetention,deferred (PI/packages/durable/src/harness/types.ts:477-487). Do not set `metadata` for SIWC (OpenAI rejects it; pi-ai openai-responses does not forward it though).
pi-ai has two OpenAI-plan routes in 1.3.0:
 (a) provider `openai` (id "openai", baseUrl https://api.openai.com/v1) with `auth.oauth` "Sign in with ChatGPT" (PI/packages/ai/src/providers/openai.ts:9-22). OAuth module PI/packages/ai/src/auth/oauth/openai-chatgpt.ts: public client, client_id `dynamic_agent_client` (:16), authorize/token URLs auth.openai.com (:19-20), resource https://api.openai.com/v1 (:21), HARD-CODED redirect http://127.0.0.1:1455/auth/callback (:23-25), scope incl chatgpt.tokens.use.direct (:26-27), local node:http callback server (:85-132), refresh via grant_type=refresh_token with the stored issued clientId (:208-223), `toAuth` -> {apiKey: credential.access} (:306-308). Login needs a device UUID `getDeviceId` -> `ext_agent_host_id=urn:uuid:` (:225-231). OpenAI docs agree: redirect must be an HTTP loopback on 127.0.0.1, only the port may vary (RAW/siwc-sign-in.md:36, https://developers.openai.com/siwc/token-sharing-open-source/sign-in.md).
 (b) legacy `openai-codex` provider (chatgpt.com/backend-api, "OpenAI Codex (legacy)", PI/packages/ai/src/providers/openai-codex.ts:7-21); superseded (PI/packages/ai/CHANGELOG.md:186). It sends instructions, store:false, stream:true, previous_response_id on websockets (api/openai-codex-responses.ts:553-558, 94, 1475). OpenAI docs say NOT to use backend-api for the plan flow (RAW/siwc-models-and-inference.md "do not point it at ChatGPT's backend-api").
Request shape of (a) (PI/packages/ai/src/api/openai-responses.ts, v1.3.0):
- SIWC detection `isChatGPTSignIn`: provider==="openai" && baseUrl==="https://api.openai.com/v1" && apiKey given && !apiKey.startsWith("sk-") (:42-49).
- stream:true, store:false always (:361, :365). OK vs docs.
- max_output_tokens only if `!omitUnsupportedFields` (:368-370); temperature same (:372-374); prompt_cache_retention and prompt_cache_options omitted (:363-364); configuration_update (mid-convo effort) disabled for SIWC (:107-110). All match OpenAI's unsupported list.
- previous_response_id: never sent by this provider (rg: no match in openai-responses*.ts). Full history is sent in `input` (convertResponsesMessages, openai-responses-shared.ts).
- System prompt: NOT sent as `instructions` (rg: no match). Sent as input item role "developer" when model.reasoning (and compat.supportsDeveloperRole !== false), else role "system" (openai-responses-shared.ts:231-243). OpenAI doc: "Use instructions or developer messages; explicit {type:message, role:system} items are rejected" (RAW/siwc-preview-limitations.md). So reasoning models OK; NON-reasoning catalog models (gpt-4, gpt-4.1, ...; RAW/ai/package/dist/providers/data/openai.json `reasoning:false`) would emit role "system" and fail on SIWC; pi-ai has no SIWC special-case there. Pick reasoning models (gpt-6-sol, gpt-6.1-sol, gpt-5.x...). Mid-conversation system updates also go out as developer items (shared.ts:241-243), allowed.
- Tools: additional_tools item used when model.compat.supportsAdditionalTools (shared.ts:198-205), which docs allow; tool_search_call fallback (shared.ts:206-222) is unsupported on SIWC, but catalog models with supportsToolSearch also set supportsAdditionalTools, so additional_tools wins (checked data json).
- Still sent and NOT on OpenAI's rejected list (so likely fine, unverified live): prompt_cache_key (:362), include:["reasoning.encrypted_content"] (:402), reasoning.summary:"auto" (:398-401), service_tier only if set (:376).
- `resolveSamplingParams` can Object.assign extra params (temperature/top_p) from model.samplingParams or request samplingParams (:411-415, simple-options.ts:24-34) with NO SIWC filter. Catalog openai models have none (data json), pi-durable passes none, so OK unless a custom model is defined with samplingParams.
- streamSimple sets maxTokens from model.maxTokens always (simple-options.ts:46) but it is dropped for SIWC at :368.
- Subscription limit error mapped: `subscription_sharing_usage_limit_exceeded` -> link to chatgpt.com/settings/usage (:255-258).
Does PiHarness/pi-durable itself handle SIWC constraints? No: neither contains any ChatGPT/SIWC/OAuth logic (rg of AG/packages/agents/src/models, harness/pi, docs: zero hits). The constraints are handled one layer down in pi-ai's openai-responses provider. So the answer to "can my pi durable instance take care of that" is yes via `openaiProvider()` in pi-ai >=1.0.x line (the SIWC support was added to pi-ai per PI/packages/ai/CHANGELOG.md:180).
OpenAI primary docs (fetched): preview-limitations (store:false, stream:true, input array, instructions or developer messages, unsupported list: background, conversation, max_output_tokens, max_tool_calls, metadata, moderation, multi_agent, prompt, prompt_cache_retention, safety_identifier, temperature, top_logprobs, top_p, truncation, user; omit previous_response_id over HTTP; tool_search unsupported) https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations.md. DevKit official sender sends model,input,instructions,store:false,stream:true only, roles user/assistant/developer, "Put system guidance in instructions" (DK/packages/local/src/responses.ts:10-14,41-47).
Hosted/remote use: overview says docs are for "open-source and locally hosted apps"; paid or remotely hosted needs the interest form (RAW/siwc-token-sharing-open-source.md; https://developers.openai.com/siwc/token-sharing-open-source.md). Self-hosted VMs: credentials may be transferred, but host-specific attribution/revocation not yet available (siwc-self-hosted-vms.md:28). Also DECISIONS.md already records the SIWC terms (local only, no cross-user use).
Cloudflare/workerd blocker (inferred, not run): pi-ai loads the OAuth module through `import(variableSpecifier)` "so bundlers cannot follow" (PI/packages/ai/src/auth/oauth/load.ts:1-12, dist/auth/oauth/load.js same). `lazyOAuth` routes login, refresh AND toAuth through that loader (auth/helpers.ts:40-59). A Worker bundle would therefore not contain openai-chatgpt.ts, and the module also imports node:http and node:crypto (dist/auth/oauth/openai-chatgpt.js:7-8). `registerBundledOAuthFlowLoaders` exists (load.ts) and `registerBunOAuthFlows` in `@earendil-works/pi-ai/bun-oauth` statically imports all flows, but that is Bun-oriented. Safest: write ~25 lines in the app: an `OAuthAuth` object {name, refresh (fetch POST to https://auth.openai.com/api/accounts/oauth/token with grant_type=refresh_token, client_id=<issued>, refresh_token, resource), toAuth: async c => ({apiKey: c.access}), login: unsupported}, and build the provider as `{...openaiProvider(), auth: {...auth, oauth: myOAuth}}` or via `createProvider` (exported from pi-ai models.ts:~1096). Provider id MUST stay "openai" and baseUrl https://api.openai.com/v1 or `isChatGPTSignIn` is false and the forbidden fields get sent. The code login flow (loopback 127.0.0.1:1455 + CLI) must happen on the user's machine; the token set is then delivered to the app (that is what "Self-hosted VMs" transfer describes).

## 4. Token refresh / per-request credential
Hook = pi-ai `CredentialStore` passed to `createModels({credentials})` (PI/packages/ai/src/models.ts:373-377, 404-408). Interface read/list/modify/delete keyed by providerId, `modify` must serialize (auth/types.ts:65-94). On every request `Models.streamSimple` -> `applyAuth` -> `getAuth` -> `resolveProviderAuth` (models.ts:849-880, 907-914): reads the stored credential; if OAuth and expiring within 5 min (or 3 min margin baked into `expires`) it calls `oauth.refresh` under `credentials.modify` (double-checked locking, 15s timeout, rotated refresh token persisted before lock release) then `oauth.toAuth` -> apiKey (auth/resolve.ts:102-191). Result: apiKey added to request options (models.ts:871). pi-durable gives no per-request `apiKey`/`getApiKey` callback: ConversationStreamOptions has no apiKey (types.ts:477-487) and `beforeRequest` hook only replaces messages (generation.ts:209-212, README:520). Per-user design: one DO per app user (name = user id) holds its own CredentialStore (DO SQLite/KV rows), or a single Models with a CredentialStore that reads the current DO's row. `InMemoryCredentialStore` is the default and is NOT durable (auth/credential-store.ts:6-12) so a custom store is required. Because Models is per-isolate and PiHarness factory runs once per isolate (pi.md:66), put the store inside the DO instance (`this.ctx.storage`).
Token facts (OpenAI docs): access token 1h; refresh token 30 days, each refresh returns a replacement refresh token (rotating); serialize refreshes per session (RAW/siwc-token-reference.md:13-15, siwc-profiles-and-sessions.md:34-38). pi's refresh requires credential.clientId (issued client) (openai-chatgpt.ts:208-212). Credential shape: {type:"oauth", access, refresh, expires, clientId, scopes} (openai-chatgpt.ts:173-180).
One ChatGPT account on several app users: OpenAI says one client_id can be reused across hosts for the same user+workspace, each host needs its own `ext_agent_host_id` (overview). Terms banning serving other users are in DECISIONS.md (not re-verified here).
