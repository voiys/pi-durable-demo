## 1. How a tool is defined

### 1a. pi-durable (what PiHarness runs): `ToolRegistration`
`PI13/packages/durable/src/harness/types.ts:293-333`:
- Extends pi-ai `Tool<TParameters>`: `{ name, description, parameters: TSchema, constrainedSampling? }` (`PI13/packages/ai/src/types.ts:754-759`). Only these `Tool` fields enter the transcript (types.ts:290).
- Extra fields: `replay?: "safe"|"unsafe"` (default unsafe, :298), `executionMode` (:300), `prepareArguments` (:306), `structuredOutputSchema` (:311), `callers?: ("model"|"tools")[]` (:317), `deferred?: true` (:322), `outputLimits` (:323).
- `execute(args: Static<TParameters>, api: ToolExecutionApi<TDetails>, context: Context): Promise<ToolExecutionResult<TDetails>>` (:328-332). Args are validated against `parameters` before `execute` (README:164).
- `defineTool()` is an identity helper that infers `args` from `parameters` (`PI13/packages/durable/src/harness/define.ts:12-17`). Tools are bundled in `defineExtension({ name, tools, sections, hooks, wraps, tasks })` (`types.ts:365-374`) and installed with `registry.install(ext)` (`types.ts:399`). Cloudflare uses a plain object the same way (`CF/examples/next/harnesses/pi/src/server.ts:46-50`).
- `ToolExecutionApi` (`types.ts:205-287`): `taskId`, `conversationId`, `callId`, `agent()`, `models`, `env` (a pi `ExecutionEnv` for shell/files, NOT the Worker env), `output(chunk)` streaming (:221), `retainedOutput()`, `diagnostic()`, `details(value, ctx)` (:236), `commit(tx => ...)` (:237), `memo(name[, candidate], ctx)` (:238-239), `createTask`, `getTask`, `waitForTask`, `conversation(id)` (:253), `executeTool(name, args, ctx, {key, progress})` (:281). It extends `DocumentReader`, so `api.snapshot(Doc, conversationId, ctx)` works (used at `PI13/packages/durable/test/examples/23-subagent-background.ts:154,166`).
- Abort: `context.abortSignal` (`PI13/packages/chord/src/context/index.ts:10`). Cloudflare's example passes it through (`workspace.ts:132`). A tool that ignores it hangs `conversation.abort()`, which has no grace period (`CF/examples/next/harnesses/pi/NOTES.md:195-199`).
- Result (`ToolExecutionResult`, `types.ts:154-170`): `output` (model-visible text/image blocks), `structuredOutput` (for programs/`executeTool` callers, only with `structuredOutputSchema`), `isError`, `details` (UI; defaults to last `details()` value), `diagnostics`, `usage`, `control` (`terminate`, `handoff`, `addTools`). A throw becomes an error result (README:181). Streaming: `api.output(chunk)` becomes the output if `output` is omitted (README:164); `api.details()` and running output are published to `pi.live` tool slots (`PI13/packages/durable/src/harness/live.ts:11-34`).
- Minimal example (1.3.0 names): README:164-179. A real third-party read-only tool set on pi-durable: `OPTD/src/memory/tools.ts:77-140` (`defineTool`, `replay:"safe"`, `api.commit`, `api.memo("timestamp", Date.now(), context)` for a replay-stable value). It returns `{ content }` because it targets Pi 1.1.0 (`OPTD/README.md`: qualified against Pi 1.1.0); on 1.2+ use `output`.

### 1b. Non-durable pi layers (reference only; NOT used by PiHarness)
- `AgentTool` (pi-agent-core): `PI13/packages/agent/src/types.ts:466-499`: `label`, `prepareArguments`, `outputSchema`, `execute(toolCallId, params, signal?, onUpdate?) => AgentToolResult{content, details, structuredContent?, isError?, terminate?}` (:424-446, :483-488), `replay?: "never"|"safe"` (:490), `executionMode`. Streaming = `onUpdate(partial)`; abort = `signal`.
- Coding-agent extension API: `ToolDefinition` `PI13/packages/coding-agent/src/core/extensions/types.ts:579-668`, registered via `pi.registerTool(...)` (e.g. `PI13/packages/coding-agent/src/extensions/codemode/index.ts:34`); adds `label`, `promptSnippet`, `exposure`, `namespace`, renderers, `execute(toolCallId, params, signal, onUpdate, ctx)` (:650-656). pi-optchat uses this API (`OPT/src/index.ts:509,518`, `OPT/src/agents.ts:305-318`).
- These tools cannot be dropped into PiHarness as is: different arg order, `content` vs `output`, `onUpdate` vs `api.output`, `signal` vs `context.abortSignal`, replay vocabulary (`never` vs `unsafe`).

## 2. Registering custom tools with PiHarness and reaching other DOs

- PiHarness takes a factory: `new PiHarness({ harness: ({storage, context}) => Harness.open(storage, { models, registry }, context), defaults })` (`CF/packages/agents/src/harness/pi/harness.ts:116-118, 156-161`; docs `CF/docs/agents/harnesses/pi.md:21-59`). Custom tools = whatever you `registry.install(...)` into the registry passed to `Harness.open`. The factory runs inside `onStart`, once per isolate (`harness.ts:250-259, 530-538`; docs pi.md:66), so installs happen again on every wake. That is required because pi stores only extension names, not code (`PI13/packages/durable/README.md:210`).
- `execute` runs inside the DO that owns the PiHarness: tool tasks are run by pi's in-memory scheduler in that DO's isolate, kept alive by the wake job (`harness.ts:463-492`). Not in a separate worker.
- Worker env/bindings: the tool is a closure created in the DO class, so it captures `this.env`, `this.ctx`, `this.harness`, `this.workspace`. This is exactly Cloudflare's example (`createWorkspaceTools(this.workspace)` at `server.ts:49`, `workspace.ts:100-137`; `new Workspace({ storage: this.ctx.storage, backends:[... loader: this.env.LOADER]})` at `server.ts:29-41`). `api.env` is NOT the Worker env (`types.ts:216`). No pi-side env injection exists (verified by absence in types.ts).
- Reaching other DOs (inferred from verified building blocks; no Cloudflare example does exactly this under PiHarness):
  - Same-DO siblings: `PiHarness.sessions.list()` returns `{id, parent?, busy}` for every conversation, including those subagent tools created (`harness.ts:736-756`; docs pi.md:186). `harness.session(id)` offers `submit`, `steer`, `wait`, `abort`, `messages()`, `busy()`, `events()` (`harness.ts:611-691`). Inside a tool, `api.conversation(id)` + `api.snapshot(LiveDoc, id, ctx)` read the same data (`types.ts:253`; example 23 :166).
  - Other top-level DOs: Cloudflare's guidance for "many chats/sessions per user" is one top-level DO each plus a per-user index DO, NOT facets (`CF/docs/agents/sub-agents.md:7, 445-483`; example `CF/examples/next/routing`). From a tool: `getAgentByName(this.env.X, name)` (`CF/packages/agents/src/agent-routing.ts:390-417`; calls `__unsafe_ensureInitialized`, so the class must be an `Agent`) or native `this.env.X.getByName(name)` RPC for the plain `DurableObject + Lifecycle.install` style Cloudflare's PiHarness examples use (`server.ts:22,76`). Lifecycle doc: use `idFromName/getByName` (`CF/docs/agents/lifecycle.md:484-492`); an `Agent` auto-starts lifecycle for async RPC methods, a plain DO must `await this.lifecycle.start()` in its RPC methods (lifecycle.md:463-482). PiHarness guards its own operations with `lifecycle.ready()` (lifecycle.md:195-196), so a cold RPC waits for the open.
  - Facets / `this.dynamicAgents.get(Cls, name)`: children whose code and lifecycle the parent supervises, reachable only through the parent, every WebSocket frame fans through the root (`sub-agents.md:95-103, 421`). Not a fit for user-visible sibling sessions.
- v1 tool list mapped onto verified APIs:
  1. list sibling agents: same-DO -> `PiHarness.sessions.list()`; cross-DO -> RPC to the per-user index DO (pattern `sub-agents.md:462-483`). Read-only so `replay:"safe"`.
  2. send message to another agent: `session.submit(input, { operationId, whenBusy })`. pi dedupes by `requestId` and PiHarness `enqueue` is idempotent per `operationId` (`harness.ts:357-396`, `accepted` flag). To make the tool `replay:"safe"`, derive the id once with `api.memo("op", crypto.randomUUID(), context)` (first writer wins and is durable: `PI13/packages/durable/src/harness/scheduler.ts:1640-1655`); a rerun resubmits the same operationId and is a no-op. Example 23 does the same with `requestId: subagent:${reporter.id}` (23-subagent-background.ts:90). Cross-DO: the target DO exposes an async RPC calling `harness.submit` (inferred). Prefer `submit` (returns once admitted, harness.ts:292) over `prompt` so two DOs never wait on each other.
  3. get last message: `session.messages()` returns pi `EntryRecord[]` since the newest reset (`harness.ts:675-678`); take the last `pi.assistant` entry's `model[0]` and join text parts (`assistantText` is internal, `harness.ts:182-188`).
  4. status + last tool call: `session.busy()` (`harness.ts:686-690`) and `pending()` (:317-334) for status. `pi.live` holds only the CURRENT round's tool slots `{callId,name,status,output,details}` (`live.ts:82-109`), so for the last finished call read the transcript (assistant `toolCall` parts and `pi.tool-result` entries).
  5. other sessions of the same user: not provided by pi or PiHarness; needs a per-user index DO (sub-agents.md:462-483) or, if all sessions are conversations of one per-user DO, `sessions.list()`.

## 3. Durability semantics of an in-flight tool call

Verified in code (`PI13/packages/durable/src/harness/tool.ts`):
- Each call is a `pi.tool` task. Phase `call` validates, runs `beforeTool` hooks, and commits an `execute` intent `{arguments, replay}` BEFORE running `execute()` (tool.ts:129-171, intent :169).
- Recovery from phase `execute`: rerun iff the stored replay is `safe` AND the currently installed tool is still `safe` (tool.ts:174-187). Otherwise the model gets an `interrupted` error result "was interrupted and may have partially run" (tool.ts:188-191) and conversations/tasks the call owned are aborted. Default is `unsafe` (types.ts:297-298). A call that never reached `execute` is simply redone.
- PiHarness does the waking: one Lifecycle job per session; after eviction the job is still due, its alarm restarts the DO, pi reopens and resumes (`harness.ts:204-213, 445-492`; docs pi.md:190-194). `onStart` creates wake jobs for every session with live tasks, including conversations created by subagent tools (`harness.ts:250-259`). Cloudflare tests: a replay-safe tool reruns after a kill, an unsafe one is reported as interrupted and not rerun (`CF/packages/agents/src/harness/pi/tests/harness.test.ts:62-72, 87-92`); they use `abortAllDurableObjects()` because graceful `evictDurableObject` waits for the in-flight step.
- Idempotency is yours: a replay-safe tool with external effects needs its own idempotency (README:232; `executeTool` doc types.ts:261-268). Tools to use: `api.memo` (first-writer-wins per task; memos vanish when the task's outcome is decided, scheduler.ts:1640-1655, :1913-1916), `operationId` for submits, `api.commit` for state.
- A plain tool has no mid-`execute` checkpoint: it restarts from the top (inferred from tool.ts:179-186). Long work should be split into pi tasks (`api.createTask`, phases with checkpoints) or nested `executeTool` calls (a replay-safe caller gets finished nested calls back by key, README:232).
- Long-running/background:
  - Foreground work runs inside the wake's `waitForIdle`, bounded to 10 min per alarm invocation (alarm handlers have a 15 min wall limit), after which the job re-arms (`harness.ts:49-63, 494-510`; NOTES.md:153-160). One model stream over 15 min is "at the platform's mercy" (NOTES.md:159-160).
  - Background tasks (example 23 anchor/reporter) are excluded from idle waits. When only background tasks remain, the wake reschedules a 30 s heartbeat and re-checks (`harness.ts:479-480`; NOTES.md:112-119 "Background work is polled"). pi's own timers (`runtime.sleep`, retry backoff) are in-memory. PiHarness only hands generation retry/poll deadlines (read from `LiveDoc`) to the alarm (`harness.ts:564-576`); a custom task's `runtime.sleep` is invisible to the wake (NOTES.md:131-137). Custom background tasks work, long sleeps inside them are not alarm-backed.
  - `abandonOnRestart` applies to tasks the creator only awaits in memory; nested calls of non-replay-safe tools and their `api.createTask` children get it by default (types.ts:240-243; README:255-258).
- Abort: `conversation.abort()` waits until idle. Owned children are aborted with the call; background tasks survive unless `abort(ctx, {background:true})` (README:538-574; NOTES.md:195-199).

## 4. Sub-agents

- pi-durable has NO built-in `subagent` tool (`rg -i subagent PI13/packages/durable/src` returns nothing). It ships primitives (task-owned conversations `tx.createConversation({ownership:{kind:"task", taskId}})`, `configure(tx, id, {...})`, `api.conversation(id)`, background tasks) and two documented product-code patterns under `test/examples` (README:538-579; table README:746-747):
  - 22 foreground: the tool creates a child conversation owned by the call, submits one task with a stable `requestId`, waits, returns the answer. `replay:"safe"` because a rerun finds the child via `scanConversations({ownerTaskId})` and the same submission (`PI13/.../test/examples/22-subagent-foreground.ts:39-77`). The child drops the subagent extension so it cannot recurse (:59).
  - 23 background: one `subagent` tool with spawn/send/stop/status. Children are owned by a background `Anchor` task; each message is delivered by a background `Reporter` task that posts the child's answer back to the parent as a `followUp` input with request ids (`23-subagent-background.ts:61-126, 132-207`). A document `Subagents` maps names to conversations (:46-54); status = `LiveDoc.run !== undefined` (:166). The tool is `replay:"unsafe"` (:146).
- PiHarness exposes children as sessions (docs pi.md:186) but adds no subagent API. Its example NOTES say examples 22/23 "should work unchanged as registered tools. The background variant needs the live work keep-alive" (`NOTES.md:272-274`); the 30 s heartbeat at `harness.ts:480` is the partial answer. NOT verified end to end: no subagent test found in `harness.test.ts`.
- Not to be confused with Cloudflare "sub-agents", now "dynamic agents" (facets): child DOs colocated under a parent with own SQLite and no alarms of their own (`CF/docs/agents/sub-agents.md:1-19, 93-103`).
- Mario's approach (coding-agent): "skips features like sub-agents" (`PI13/packages/coding-agent/README.md:19`); the shipped example extension runs each subagent as a separate `pi` process (`PI13/packages/coding-agent/examples/extensions/subagent/README.md:7-12`). Not usable in a DO (no processes).
- Alternatives read in this run:
  - pi-optchat (non-durable pi extension): tools `spawn`, `tell`, `tell_parent`, `models` (`OPT/src/agents.ts:305-318`). Children report automatically as a message ("never poll or sleep waiting", agents.ts:305); caps on depth and active agents; inspector tree with state, elapsed, current tool; cut-off children resume on next open (OPT/README.md, "Subagents" section).
  - optchat-durable (kevinqz, on pi-durable): packaging reference for "extension = sections + tools + tasks + hooks" (`OPTD/src/extension.ts:36-70`, `OPTD/src/memory/tools.ts`); no subagent tools.
  - Cloudflare "agent tools" (`CF/docs/agents/agent-tools.md`) are for Think/AIChatAgent children, not PiHarness.
  - Peer agents as separate top-level DOs plus a per-user index (sub-agents.md:445-483): closest published Cloudflare pattern for "sibling agents + other sessions of the same user".
- Suggested v1 vocabulary (my design, not verified behavior): `agents_list`, `agent_send` (operationId via memo; `whenBusy` steer vs followUp), `agent_last_message`, `agent_status`, `sessions_list`. Read-only ones `replay:"safe"`; `agent_send` safe iff the operationId is memoized.

## 5. SIWC Responses constraint vs how pi serializes tools

Constraint (verified): "Supported tools: Group function/custom tools in namespaces or supply them through `additional_tools` input items." Unsupported: image generation, file search, Code Interpreter, native computer use, hosted MCP/connectors, Responses `tool_search`; `programmatic_tool_calling` not accepted in top-level `tools` (SIWC preview-limitations.md:14-15). Also `store:false`, `stream:true`, omit `temperature`, `max_output_tokens`, `previous_response_id`, `prompt_cache_retention`, ... (:11-13).

What pi 1.3.0 does (verified, `PI13/packages/ai/src`):
- First-class SIWC handling: `isChatGPTSignIn(model, apiKey)` = provider `openai` + baseUrl `https://api.openai.com/v1` + key not starting `sk-` (`api/openai-responses.ts:38-49`). When true it drops `prompt_cache_retention`, `prompt_cache_options`, `max_output_tokens`, `temperature` (:355-374) and `configuration_update` items (:106-114) and always sets `store:false`, `stream:true` (:358-366). Test: `ai/test/openai-responses-chatgpt-sign-in.test.ts:44-61`. SIWC login is an OAuth on the `openai` provider (`providers/openai.ts:14-20`). It does nothing special about tools.
- Tool serialization: `convertResponsesTools` (`api/openai-responses-shared.ts:385-422`) emits flat `{type:"function", name, description, parameters, strict}` (or `{type:"custom", format:grammar}` for grammar-constrained tools, :392-404). pi-ai has NO namespace grouping of tool definitions; `namespace` exists only as a field preserved on tool CALLS (`ai/src/types.ts:442-443`; `openai-responses-shared.ts:333,342,517,538,742,758`).
- Placement (`openai-responses.ts:331-385`, `utils/transcript.ts:199-237`): `resolveTranscriptTools(messages, supportsAdditionalTools || supportsToolSearch)`. If the model supports additions and no tool was removed/redeclared, the INITIAL system message's `toolsAdded` go flat in top-level `params.tools`, and later `toolsAdded` ride in `{type:"additional_tools", role:"developer", tools:[...]}` input items anchored at their system message (`openai-responses-shared.ts:195-205`, same flat converter). Otherwise the whole current list goes flat at top level (transcript.ts:232-235). The `tool_search_call/_output` path (shared.ts:206-222) is only used when `supportsAdditionalTools` is false.
- Catalog flags (published pi-ai 1.3.0 tarball, `raw/pitools/piai/package/dist/providers/data/openai.json`, parsed with node): `gpt-5.4, 5.4-mini, 5.4-pro, 5.5, 5.6-luna/sol/terra, gpt-6-astra, gpt-6-luna, gpt-6-sol, gpt-6.1-sol` have `supportsAdditionalTools:true, supportsToolSearch:true, supportsMidConvoSystemMessages:true` (`gpt-5.4-nano`, `gpt-5.5-pro` do not). Generator: `PI13/packages/ai/scripts/generate-models.ts:375-398, 927-939`.
- pi-durable feeding: tool changes are stored as positional `pi.system` entries with `toolsAdded/toolsRemoved` (`PI13/packages/durable/src/harness/prompt.ts:66-119`). First request = baseline with all tools -> flat top-level `tools`. A tool added later (new extension, `control.addTools`, tool_search load) -> additive `additional_tools` item. Changing a tool's description/schema, or removing one, is remove+re-add = non-additive -> the whole list flat at top level again. Practical rule: keep each conversation's tool set stable and install all custom tools before its first turn.
- Codex on the same endpoint (verified, snapshot 2026-09-07): models with `use_responses_lite=true` send NO top-level `tools`; they put all tools in an `additional_tools` input item, every function/custom tool wrapped in a namespace named `functions` (`type:"namespace", name:"functions", tools:[{type:"function"|"custom",...}]`), with instructions as a developer message (`CODEX/codex-rs/core/src/client.rs:902-939`, `CODEX/codex-rs/tools/src/tool_spec.rs:95-135`, test `tools/src/tool_spec_tests.rs:164-227`, `DEFAULT_FUNCTION_NAMESPACE="functions"` `protocol/src/tool_name.rs:7`). `use_responses_lite` is model metadata (`protocol/src/openai_models.rs:477`); in the bundled catalog it is true for `gpt-6-astra`, `gpt-5.6-sol/terra/luna`, false for `gpt-5.5`, `gpt-5.4*`, `gpt-5.2` (`CODEX/codex-rs/models-manager/models.json`, read with node). Non-lite models get flat top-level `tools` (client.rs:934-938).
- Gap/risk (UNVERIFIED; needs a live smoke test with the owner's SIWC token, which cannot be done here): pi's first request for gpt-6.x puts flat function tools in top-level `tools`. The SIWC sentence can be read as "flat top-level tools are not accepted", and Codex's Lite path never sends top-level tools. I found no pi test or changelog entry showing pi + SIWC + custom tools working on a Lite model, and the Codex snapshot predates `gpt-6-sol`/`gpt-6.1-sol`, so their Lite flag is unknown. Also `supportsToolSearch:true` is set in the catalog although SIWC rejects `tool_search`; it should not be reached while `supportsAdditionalTools` is true (shared.ts:198-206).
- If the smoke test fails, options (inferred, none verified): (a) wrap the `openai` provider so its stream call passes pi-ai's `onPayload` hook (`ai/src/api/openai-responses.ts:203`; ai README:1160) and rewrites `tools` into an `additional_tools` input item with a `functions` namespace; pi-durable's `ConversationStreamOptions` has no `onPayload` (`durable/src/harness/types.ts:477-487`) and generation calls `runtime.models.streamSimple` (`generation.ts:431`), so the hook must be injected at the `Models` provider layer; (b) report upstream.
