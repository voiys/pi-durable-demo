## 2. OAuth contract (sign-in.md, profiles-and-sessions.md, token-reference.md)
- Discovery https://auth.openai.com/.well-known/openid-configuration; issuer https://auth.openai.com; authorize https://auth.openai.com/api/accounts/authorize; token https://auth.openai.com/api/accounts/oauth/token; JWKS https://auth.openai.com/.well-known/jwks.json (website.md:44-48); revocation_endpoint from discovery (profiles-and-sessions.md:27).
- Authorize params (sign-in.md:28-42): client_id=dynamic_agent_client (first time) else saved issued client_id (oaiapp_...); agent_name_hint (first reg only, app name); ext_agent_host_id (required); id_token_hint / login_hint (reauth); response_type=code; redirect_uri; scope "openid profile email" + "offline_access resource.invoke chatgpt.tokens.use.direct"; resource=https://api.openai.com/v1; state; nonce; code_challenge_method=S256; code_challenge.
- redirect_uri: "HTTP loopback callback on 127.0.0.1 from initial registration onward, e.g. http://127.0.0.1:1455/auth/callback... only the port may vary. Keep scheme, host, path unchanged: /callback does not match /auth/callback... Do not substitute localhost" (sign-in.md:36). Docs never discuss a web app served on 127.0.0.1; a dev server route at 127.0.0.1:<port>/auth/callback satisfies the stated URI shape (inferred, untested). Non-loopback unsupported: @lucasmeijer 2026-09-30 / 2026-10-06 (read) "does not support non localhost redirect". self-hosted-vms.md:10: 127.0.0.1 callback reaches the browser's machine, not the VM; complete OAuth locally and transfer credentials. pi (pi-source-v1.3.0 packages/ai/src/auth/oauth/openai-chatgpt.ts:22-25,266-279) uses 127.0.0.1:1455/auth/callback AND offers "paste the final redirect URL" manual fallback -> workable for a remote backend. npm @reforma/siwc-bridge (MIT, 2026-10-01) redirects loopback callback to a remote backend (third-party; its README warns OSS/dev use only).
- Callback new reg: code, state, client_id (issued), scope. Exchange: POST form grant_type=authorization_code, client_id=issued, code, code_verifier, redirect_uri, resource; no secret (public client). Do not save dynamic_agent_client.
- Token response: access_token, refresh_token, id_token, token_type, expires_in (3600), scope, earliest_refresh_at. Refresh token 30 days, rotating, each refresh gives new 30d token (token-reference.md:10-12). Refresh: grant_type=refresh_token, issued client_id, refresh_token, resource; omit scope; serialize refreshes. Refresh errors that require re-auth: invalid_grant, invalid_refresh_token, token_expired, refresh_token_expired/invalidated/reused (errors-and-recovery.md).
- ID token validation: JWKS sig, iss, aud == issued client_id, exp, nonce; sub = identity; RS256 in devkit (oauth.ts verifyIdentity). Access token claims: sub, aud=https://api.openai.com/v1, client_id, scope, iss, exp ... opaque auth metadata.
- ext_agent_host_id formats (token-sharing-open-source.md): urn:ietf:params:oauth:jwk-thumbprint:... (preferred), urn:uuid:<uuidv4>, did:key:<key>. Opaque, not email/user id; "not an authentication credential"; not verified by OpenAI.
- Must check granted scope contains chatgpt.tokens.use.direct; access_denied -> plan usage off.

## 3. Account linking design
- Docs: client = per authenticated user+workspace registration; host = environment (laptop/VM); "A single client can have multiple hosts for the same user and workspace... each host must have its own distinct host identifier." Host id is per installation/VM, never per app user.
- website.md:342-346: explicit linking policy; a signed-in user can add ChatGPT as a method, email match alone not proof. But that page is the identity-only (waitlisted commercial) flow. For OSS plan usage, docs (profiles-and-sessions.md:4-23) describe multiple ChatGPT account registrations per installation, each with own client_id+creds, same host id.
- Linking email/password user -> "connect ChatGPT plan": not discussed as a pattern for hosted multi-user apps; technically each app user would run own dynamic registration (client_id per user), with host id for the app deployment (or per user - docs say per host; unverified what OpenAI does with many users on one host id). Many users each connecting their OWN ChatGPT account on one hosted server = "remotely hosted app" => waitlist. Same ChatGPT account for several app users: not covered by docs; Tibo's sharing statement says flagged. Demo of user A + user B each with own plan, run locally, is the defensible shape.
- self-hosted-vms.md:25: host-specific usage attribution/revocation for transferred sessions not yet available.

## 4. Responses API constraints (preview-limitations.md, models-and-inference.md)
- POST https://api.openai.com/v1/responses, Bearer access token; NOT chatgpt backend-api. store:false and stream:true required. input array with full history. Use instructions or developer messages; {type:message, role:system} rejected. Omit previous_response_id (HTTP), background, conversation, max_output_tokens, max_tool_calls, metadata, moderation, multi_agent, prompt, prompt_cache_retention, safety_identifier, temperature, top_logprobs, top_p, truncation, user.
- Tools: function/custom tools must be grouped in namespaces or supplied via additional_tools input items. Unsupported: image gen, file search, code interpreter, native computer use, hosted MCP/connectors, tool_search, programmatic_tool_calling. Web search subject to policy. Inputs: text/images/files if model accepts; no audio/video.
- Models: GET https://api.openai.com/v1/models with same token -> {models:[{slug,display_name,visibility}]}; show visibility=="list". Example model gpt-6.1-sol.
- Success only on response.completed; response.failed codes: subscription_sharing_usage_limit_exceeded (429), ..._usage_unavailable (503), ..._unsupported_capability (400, error.param), ..._user_not_eligible (403), ..._invalid_user (401) etc. Pre-stream errors may be {"detail":..}. Plus: 5-hour limit shared across apps; users manage at chatgpt.com/settings/usage.
- Codex app-server alternative: codex-app-server.md (env_key ACCESS_TOKEN provider, stdio).

## 6. better-auth
- No SIWC provider/plugin: npm search (siwc, "sign in with chatgpt", "better-auth chatgpt") finds none for better-auth; better-auth issue #11472 "feat: add a Sign in with ChatGPT" OPEN (2026-09-29); maintainer bytaesu: will work on it "once it's GA on OpenAI-side or I can get an OAuth client... not a priority". Other npm packages are pi/dsh/open-webui style (pi-chatgpt-pool, @reforma/siwc-bridge, @byokit/accounts - not read).
- better-auth latest 1.7.10 (npm dist-tags; ctx better-auth-1710-source, commit b734a418). genericOAuth (packages/better-auth/src/plugins/generic-oauth/types.ts): supports discoveryUrl (ID token JWKS+nonce verification by default), pkce default true, authorizationUrlParams (static; can carry resource, ext_agent_host_id, agent_name_hint), scopes, clientId w/o clientSecret (token auth "none" supported via tokenEndpointAuth), getToken override, tokenUrlParams, refreshTokenParams, accountSubject. /link-social (api/routes/account.ts:126-209) accepts per-request additionalParams (reserved keys state/client_id/redirect_uri/... rejected), scopes, additionalData, loginHint.
- Blockers: (a) clientId is static per provider config, but SIWC needs client_id=dynamic_agent_client at authorize and the ISSUED client_id (from callback query) at token exchange + ID token audience; core callback (api/routes/callback.ts:200-206) calls provider.validateAuthorizationCode with only code, codeVerifier, deviceId, redirectURI -> callback client_id is never passed; ID-token audience check uses static c.clientId (generic-oauth/index.ts:268). So genericOAuth cannot complete dynamic registration without a custom plugin/route. (b) redirectURI is baseURL + /callback/<id> (oauth2/utils.ts:39-47), cannot be http://127.0.0.1:port/auth/callback unless baseURL/basePath arranged or provider.callbackPath set via custom provider. (c) account key (providerId, sub) is unique per user: oauth2/link-account.ts:115-121,192-223 returns ACCOUNT_ALREADY_LINKED_TO_DIFFERENT_USER / CONFLICT - same ChatGPT account cannot be linked to two app users in better-auth's account table; email must match unless accountLinking.allowDifferentEmails (link-account.ts:104-110).
- Fit: keep better-auth email/password for identity only; implement connect as own server routes + own table (appUserId, issued client_id, host id, verified sub, access/refresh/expiry, scopes) - not the better-auth account table. Optionally wrap as a small better-auth plugin (endpoints with sessionMiddleware) for auth-gated routes.
- pi reference impl of the same flow: pi-source-v1.3.0 packages/ai/src/auth/oauth/openai-chatgpt.ts (dynamic_agent_client, host id urn:uuid from device id, 127.0.0.1:1455/auth/callback, manual paste fallback, "every login registers a new client").
